## 2｜P1：AI Agent 场景识别

### 2.1 核心理解

学习 P1 后，我对 Agent 的第一个认识发生了变化：

> 不是所有 AI 功能都应该做成 Agent。

判断一个需求是否适合 Agent，需要重点关注三个维度：

1. 数据可得性；
2. 任务可定义性；
3. Agent 与 Workflow 的流程选择。

其中，数据可得性是最前置的条件。

如果完成任务所需要的数据不存在、过时、无法读取或无法接入，那么单纯更换更强的模型并不能真正解决问题。

同时，Agent 和 Workflow 也不是非此即彼。

对于第一次构建 AI 产品而言，更稳妥的方式通常是：

> 先通过 Workflow 把任务路径和数据链路跑通，再逐步增加 Agent 的自主决策能力。

### 2.2 注规学习 Agent：10 个典型问题的数据可得性练习

我选择自己准备开发的“注册城乡规划师学习 Agent / App”作为真实案例。

|#|希望 Agent 能回答的问题|主要数据来源|当前数据状态|当前可用性|
|-|-|-|-|-|
|1|某个注规知识点在教材中如何解释？|注规教材|已有资料，但需整理|需建设|
|2|某项现行规划法规具体规定是什么？|官方法规文件|数据存在且权威|较容易接入|
|3|某道真题为什么选择这个答案？|真题、答案、教材|部分已有，需结构化|需建设|
|4|这道错题对应哪个知识点？|题库、知识点体系|尚未建立完整映射|需建设|
|5|我最近最薄弱的是哪些知识点？|错题、答题记录|尚未持续积累|暂不可用|
|6|根据薄弱点生成针对性练习|错题、知识点、题库|数据尚未打通|暂不可用|
|7|当前各科复习进度怎样？|学习计划、学习记录|部分已有但较分散|需整合|
|8|网课老师在哪一节讲过这个知识点？|已购买网课视频|视频存在，尚未形成转写索引|需建设|
|9|最新政策变化如何影响考试知识点？|官方政策、教材、课程资料|数据存在但需持续更新|部分可用|
|10|根据当前进度生成下一周复习计划|进度、错题、考试日期|来自多个来源|需整合|

按“数据存在、可靠、可被机器处理且当前系统可以获得”的严格标准，目前真正可以直接用于 Agent 的数据仍然较少。

因此，这个项目现阶段最需要投入的并不是继续寻找“更强模型”，而是逐步建设：

> 教材 + 法规 + 题库 + 错题 + 网课转写 + 学习状态

组成的可靠数据底座。

### 2.3 第一阶段实施思路

注规学习系统不会一开始就追求完全自主 Agent。

第一阶段优先建立可控 Workflow：

> 用户问题  
> → 判断问题类型  
> → 查询对应资料  
> → 基于资料生成回答  
> → 提供依据  
> → 用户反馈  
> → 更新学习记录

随着数据层、评测体系和学习记忆逐渐稳定，再逐步增加 Agent 的自主决策能力。

## 3｜D1：大模型 API 工程化基础

### 3.1 代码实践结果

本次使用课程虚拟环境实际运行 D1 示例。

|示例|运行结果|主要验证内容|
|-|-|-|
|`d1\_1\_base.py`|✅ 成功|基础模型 API 调用|
|`d1\_2\_multi\_turn.py`|✅ 成功|多轮对话|
|`d1\_3\_streaming.py`|✅ 成功|Streaming 流式输出|

|`d1\_5\_tool\_use\_seekdb.py`|⚠️ 未最终跑通|Windows 下 seekdb Server 环境部署与排障|

### 3.2 再次观察到模型事实性错误

运行 `d1\_1\_base.py` 时，程序正常调用模型并成功返回结果，但模型将 RAG 错误解释为：

`Retrieval with Active Guidance`

而 RAG 正确的含义应为：

`Retrieval-Augmented Generation`

Task 01 中已经第一次观察到类似情况，本次再次复现，使我进一步确认：

> API 调用成功、程序没有报错，并不等于模型输出事实正确。

这也让我更直观地理解了后续为什么需要：

* 可靠数据源；
* RAG；
* Tool Use；
* 来源追踪；
* 输出验证；
* 评测机制。

### 3.3 Tool Use 实践

运行 `d1\_4\_tool\_use\_mock.py` 时，用户问题为：

> seekdb 支持哪些检索方式？混合检索是怎么实现的？

模型没有直接凭自身知识生成答案，而是主动调用：

`query\_knowledge\_base`

第一次查询：

> seekdb 支持哪些检索方式

获取结果后，模型继续判断现有信息不足，又第二次调用同一个工具：

> seekdb 混合检索的实现方式

这让我第一次从真实代码运行中观察到：

> 推理 → 行动 → 观察 → 再推理

的循环。

知识库只提供了 seekdb 支持关键词检索、语义向量检索和混合检索等信息，并没有给出混合检索的具体实现细节。

最终模型明确说明知识库缺少相关信息，而没有强行编造实现过程。

### 3.4 我对 Tool Use 的理解

学习前，我容易把“Agent 调用工具”理解成大模型自己执行了工具。

学习 D1 后更准确的理解是：

> 模型负责判断要不要调用工具、调用哪个工具以及传递什么参数；真正执行数据库查询、API 调用、文件读取等动作的是外部代码。

完整过程可以表示为：

> 用户提问  
> → 模型判断  
> → 产生 `tool\_call`  
> → Python 执行工具  
> → 返回 `ToolMessage`  
> → 模型读取工具结果  
> → 再次判断  
> → 最终回答

因此，Tool Use 实际上是模型推理能力与外部数据、程序和现实世界之间的连接机制。

### 3.5 seekdb Server 环境部署与排障

首次运行 `d1\_5\_tool\_use\_seekdb.py` 时出现：

`Embedded 模式依赖 pylibseekdb（当前平台未安装或不支持）`

进一步排查确认：

* 当前操作系统为 Windows；
* `pyseekdb` 已正常安装；
* 当前版本为 `1.4.0.post1`；
* 问题并非 Python 包缺失；
* Windows 环境下需要使用 seekdb Server 模式。

为此进一步完成了：

> Windows  
> → WSL  
> → Docker Desktop  
> → seekdb Docker 容器  
> → seekdb Server 启动与日志检查

Docker 容器已经能够正常运行，seekdb 内部日志也显示：

* `cluster bootstrap success`
* `observer instance start success`
* `observer start success`

但 MySQL 客户端连接 `127.0.0.1:2881` 时仍然出现连接失败，因此本次没有将 `d1\_5` 记为成功运行。

这个问题留到后续 D2 / RAG 实践前继续解决，不为了“作业显示全部成功”而虚构实验结果。

这次排障让我认识到：

> 一个真实 AI 应用能否运行，不只取决于模型 API 和 Python 代码，还依赖操作系统、运行模式、数据库、容器、环境变量和网络连接等完整工程环境。

同时也进一步认识到：

> “容器运行成功”“程序没有退出”“服务日志显示启动成功”，都不一定等价于整个应用链路已经真正可用。

## 4｜I1：AI 原生数据库基础

### 4.1 核心理解

学习 I1 后，我开始理解：

> 大模型不能替代数据库。

大模型主要提供概率性的理解、推理和生成能力，而数据库负责：

* 持久化事实；
* 保存业务状态；
* 权限控制；
* 数据一致性；
* 数据恢复；
* 精确查询；
* 检索；
* Agent 记忆与任务状态管理。

因此，“AI 原生数据库”也不能简单理解成“支持向量字段的数据库”。

一个真实 Agent 往往需要同时处理：

> 关系数据 + 文本数据 + 向量数据 + JSON / 元数据 + 权限 + 状态 + 检索

### 4.2 注规学习 Agent 的数据底座

结合自己的注规学习 Agent，可以初步划分四类核心数据。

|数据类型|具体内容|主要访问方式|
|-|-|-|
|业务数据|科目、章节、题目、答题记录、考试日期、完成状态|SQL 精确查询|
|知识数据|教材、法规、网课转写、知识点、题目解析|全文检索 + 向量检索|
|记忆数据|错题、薄弱知识点、掌握程度、学习偏好|SQL + 语义检索|
|任务状态|当前学习阶段、复习计划、待完成任务|SQL 精确查询|

### 4.3 检索链路思考

未来如果用户提出：

> 为什么这道题我总是做错？

系统可能需要同时访问：

1. 当前题目；
2. 标准答案；
3. 对应教材；
4. 相关法规；
5. 用户历史错题；
6. 当前掌握状态。

因此，真实学习 Agent 不能简单等同于“一次向量搜索”。

更完整的数据链路可能是：

> 用户问题  
> → 结构化条件过滤  
> → 全文 / 向量召回  
> → 必要时融合与重排  
> → 形成上下文  
> → LLM 推理  
> → 返回答案及依据

### 4.4 一致性与写后可见性

注规 Agent 中不同数据对更新速度的要求不同。

教材、法规等知识数据可以经过整理和审核后再进入正式数据层。

但学习状态属于动态数据。

例如：

> 用户刚刚答错一道题。

这条信息应该能够很快被下一轮练习和复习建议使用。

因此：

* 知识数据更关注来源、版本与正确性；
* 学习状态更关注及时写入和后续可见性。

### 4.5 权限、修改与恢复

当前 MVP 首先服务个人使用，因此：

* 错题；
* 学习记录；
* 学习状态；
* 个性化记忆

都属于个人私有数据。

如果未来发展为多用户产品，则必须进一步实现用户级数据隔离和权限控制。

同时，Agent 也不应该在没有验证的情况下直接修改核心学习状态。

例如 Agent 判断：

> “这个知识点已经掌握。”

更稳妥的方式应该是：

> Agent 产生候选修改  
> → 展示差异  
> → 用户或规则确认  
> → 写入正式状态

这与 I1 中 Fork → Diff → Merge 的思想具有对应关系。

### 4.6 初步技术架构

结合目前的产品规划，注规学习 Agent 第一阶段可以采用：

> 教材 / 法规 / 题库 / 网课  
> ↓  
> 清洗、分段、结构化  
> ↓  
> PostgreSQL / Supabase 等数据层  
> ↓  
> 精确查询 + 全文检索 + 向量检索  
> ↓  
> Tool Use  
> ↓  
> LLM / Agent  
> ↓  
> 答疑 / 刷题 / 错题 / 复习计划

课程实验阶段继续使用 seekdb，帮助理解统一数据层、混合检索和后续 Agentic RAG。

最终数据库方案暂不在 I1 阶段锁死，后续结合 D2、I2 等模块的真实实验结果再进一步判断。

## 5｜P1、D1、I1 串起来后的理解

完成三个模块后，我发现它们并不是三组孤立知识。

P1 回答：

> 这个问题到底值不值得用 Agent？

D1 回答：

> 模型如何真正调用工具并获得外部数据？

I1 回答：

> 工具背后的可靠数据、业务状态和记忆应该怎样管理？

三者可以串成：

> 真实需求  
> → 判断 Agent / Workflow  
> → 确定数据需求  
> → 建立数据底座  
> → Tool Use  
> → 模型推理与行动  
> → 用户反馈  
> → 持续调整

这让我开始从“使用 AI 工具”逐步进入：

> 理解一个 AI 应用为什么这样设计、怎样真正落地。

## 7｜Task 02 阶段总结

Task 01 主要解决的是：

> AI 开发学习环境能不能真正运行起来。

Task 02 开始进入：

> 一个 AI 应用为什么应该这样设计。

本阶段最大的变化，是我不再把 Agent 简单理解成“更强的聊天机器人”。

一个可靠的 Agent 至少需要同时考虑：

* 场景是否真的需要 Agent；
* 数据是否存在、可靠并且能够获得；
* 什么应该由 Workflow 控制；
* 模型应该调用哪些工具；
* 工具背后的数据是否可靠；
* 业务状态和记忆如何保存；
* 哪些自动操作必须保留人工确认。

真实代码实践也再次验证：

> 程序成功运行不等于结果一定可信；基础设施启动成功也不等于完整应用链路已经可用。

下一阶段进入 RAG 和向量数据库后，我会继续以注规学习 Agent 为主要案例，把教材、法规和题库逐步转化为真正可检索的数据。
