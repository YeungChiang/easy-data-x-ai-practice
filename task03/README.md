## 2｜P2：Agentic RAG 产品设计

### 2.1 RAG 不等于向量数据库

以前我容易把 RAG 简化理解为：

> 文档 → 向量数据库 → 相似度搜索 → LLM 回答

学习 P2 后，更准确的理解是：

> RAG 的核心是 Retrieval-Augmented Generation，重点首先是 Retrieval，也就是在生成答案之前，先从外部世界取回当前问题需要的信息。

Retrieval 并不只包含向量搜索，还可以包括：

- 全文 / 关键词检索；
- 向量语义检索；
- 标量 / 元数据过滤；
- SQL 等结构化查询；
- 图谱 / 关系查询；
- API / Tool 调用；
- 外部搜索。

因此：

> RAG ≠ Vector Search。

向量检索只是 Retrieval 中的一种手段。

---

### 2.2 为什么纯向量搜索不够

向量搜索擅长的是：

> 找“意思相近”的内容。

例如：

> “怎么设计用户权限”

即使知识库写的是：

> “访问控制架构”“RBAC 权限模型”

理论上也有机会通过语义相似度找到。

但是对于下面这些内容：

- 法规条款号；
- 产品版本号；
- 错误码；
- API 参数名；
- 精确数值；
- 专有名词；

“语义相近”并不等于“答案正确”。

例如：

`E-4011`、`E-4012`、`E-4013`

在语义空间中可能非常接近，但在真实业务里完全是三个不同错误。

因此生产级 RAG 往往需要组合：

> 向量检索 + 全文检索 + 标量 / Metadata 过滤 + 必要的结构化查询

也就是 Hybrid Search。

---

### 2.3 传统 RAG 与 Agentic RAG

学习后我认为二者真正的区别并不是：

> 一个简单，一个复杂。

而是：

> 流程中有没有可以根据中间结果自主调整的循环。

传统 RAG 即使包含：

- Query Rewrite；
- 多路召回；
- Reranking；
- 上下文压缩；
- 引用生成；

仍然通常是一条预先设计好的 DAG：

> 用户问题 → 检索 → 重排 → 生成 → 结束

Agentic RAG 则开始出现：

> 检索 → 判断证据是否足够 → 不够则改写 Query → 再检索 → 再判断 → 必要时换工具或数据源

因此 Agentic RAG 的关键变化是：

- 可以重试；
- 可以补搜；
- 可以重新路由；
- 可以多跳查询；
- 可以根据结果动态决定下一步。

这与之前学习的 Agent：

> 感知 → 推理 → 行动 → 观察 → 再推理

形成了对应关系。

## 3｜完整 RAG 的六段流程

P2 中让我印象最深的一点，是 RAG 并不只是“检索 + 生成”，而是一条完整产品链路：

> 数据准备  
> → 问题理解与改写  
> → 搜索召回  
> → 融合与重排  
> → 上下文组织与回答生成  
> → 评估与反馈

### 3.1 数据准备

包括：

- Load；
- Parse；
- Clean；
- Split / Chunk；
- Metadata 增强；
- Embedding；
- Index；
- Refresh。

这一阶段直接决定后续“有没有可能搜对”。

### 3.2 问题理解与改写

可以包括：

- Query Analysis；
- Entity Extraction；
- Query Rewrite；
- Query Expansion；
- Query Decomposition；
- Routing。

本质上是在做：

> 把用户语言转换成更适合系统检索的表达和路径。

### 3.3 搜索召回

目标是：

> 尽量不要漏掉真正需要的证据。

可以采用：

- Vector Retrieval；
- Full-text Retrieval；
- Scalar Filter；
- SQL / Structured Retrieval；
- Parent-Child Retrieval；
- 多路召回。

### 3.4 融合与重排

召回出来以后，还需要：

- 去重；
- 合并；
- RRF 等融合；
- Reranking；
- 来源与时效加权；
- 上下文压缩。

很多系统并不是“完全没搜到”，而是：

> 搜到了，但真正重要的证据没有排在前面。

### 3.5 上下文组织与生成

包括：

- Prompt Assembly；
- 来源引用；
- 约束生成；
- 结构化输出；
- 信息不足时拒答。

### 3.6 评估与反馈

RAG 不能仅靠“随机问几个问题感觉还不错”来判断效果。

需要建立持续评测与反馈闭环。

## 4｜RAG 问题归因框架

P2 给了我一个很实用的判断方式：

> 当 AI 答得不好时，不应该第一反应就是换模型。

可以按照三个层次排查。

### 数据层

典型情况：

- 知识库根本没有正确答案；
- 数据过期；
- Chunk 不合理；
- 正确资料没有召回；
- 检索到了但排名太靠后；
- Metadata / 过滤规则错误。

### 模型层

典型情况：

> 正确证据已经给到模型，但模型仍然编造、误读或没有正确使用资料。

### 业务层

典型情况：

> 内容本身事实正确，但不符合当前用户、产品规则、表达形式或业务要求。

因此可以形成：

> 先查数据覆盖  
> → 再查检索结果  
> → 再查模型是否忠于证据  
> → 最后检查业务规则与 Prompt

> 数据存在，但检索没有把正确内容召回。

归因：

> 数据层｜检索策略 / 向量召回质量

这也是本次课程中非常有价值的一个真实失败案例。

## 6｜I2：向量数据库与 RAG

### 6.1 Embedding：把语义转换成可计算表示

Embedding 模型可以把文本转换为一组高维数值向量：

> 文本 → Embedding → Vector

这样原本不能直接进行数学比较的自然语言，就可以通过向量距离或相似度进行检索。

例如：

> “忘记数据库密码怎么办？”

和：

> “如何恢复数据库访问口令？”

虽然字面差异较大，但语义相近，因此有机会在向量空间中靠得很近。

---

### 6.2 向量不是事实本身

I2 中一个很重要的提醒是：

> 向量负责帮助找到候选内容，但向量本身并不是事实证据。

向量距离近只能说明：

> Embedding 模型认为内容相似。

不能证明：

- 内容正确；
- 内容最新；
- 内容权威；
- 用户有权限查看；
- 内容一定支持最终答案。

因此 RAG 数据层还需要同时保留：

- 原始正文；
- 来源；
- 文档版本；
- 更新时间；
- 权限；
- Metadata；
- Embedding 模型及版本信息。

---

### 6.3 KNN 与 ANN

KNN 可以理解为：

> 找到距离 Query 向量最近的 K 个对象。

精确 KNN 可以遍历全部向量得到精确结果，但随着数据规模增长，成本很高。

ANN 则通过索引结构：

> 用一定程度的近似换取更快的搜索速度。

因此真实向量检索存在：

> Recall、Latency、Resource Cost

之间的权衡。

---

### 6.4 HNSW、IVF 与量化

本阶段我先建立概念层理解：

- HNSW：通过多层图结构快速寻找相近向量；
- IVF：先找到相关分区，再在部分分区中搜索；
- SQ / PQ / BQ：通过降低向量表示精度减少存储和计算成本。

目前我的重点不是调优这些底层索引参数，而是先理解：

> 向量搜索并不是完全精确搜索，而是在质量、速度和资源之间做工程权衡。

---

## 7｜Hybrid Search：混合检索

### 7.1 三种基本能力

我目前可以用下面的方式理解：

**Vector Search**

> 找“意思相近”的内容。

**Full-text Search**

> 找“字面必须准确匹配”的内容。

**Scalar / Metadata Filter**

> 规定“只能在哪个范围里找”。

三者组合后，才能更好覆盖真实业务问题。

---

### 7.2 为什么需要融合

向量搜索与全文搜索得到的分数并不是同一种尺度。

因此不能简单把：

> Vector Score + BM25 Score

直接相加。

课程介绍了 RRF（Reciprocal Rank Fusion）：

> 不直接比较不同检索器的原始分数，而更多根据各自排序名次进行融合。

现阶段我不需要背 RRF 公式，但需要知道：

> 多路检索结果必须经过合理融合，而不是简单拼在一起。

---

### 7.3 Reranking

召回阶段和重排阶段承担不同任务：

> Recall：尽量不要漏掉可能相关的信息。  
> Rerank：把真正重要的信息排到前面。

常见流程可以是：

> 大规模知识库  
> → 召回 50～200 条候选  
> → Reranker 精排  
> → 保留 5～20 条  
> → 进入 LLM Context

因此：

> Top-K 不是越大越好。

过多候选会：

- 增加 Token；
- 增加噪音；
- 增加 Rerank 成本；
- 干扰模型使用真正重要的证据。

---

## 8｜RAG 评测

### 8.1 检索层

本阶段重点理解：

**Recall@K**

> 应该找到的内容，有多少进入 Top-K。

**Precision@K**

> Top-K 中，有多少是真的相关内容。

**MRR**

> 第一个真正相关结果排在多靠前的位置。

**nDCG**

> 当结果存在不同相关等级时，评价整体排序质量。

---

### 8.2 生成层

除了检索，还需要评价：

- Faithfulness｜是否忠于证据；
- Answer Relevancy｜是否真正回答用户问题；
- 引用准确性；
- 完整性；
- 无证据时的拒答能力。

这让我意识到：

> RAG 质量不是一个指标，而是一组从检索到生成的完整评测体系。
